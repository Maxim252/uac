# Монитор безопасности UAC (Security Monitor)

**Версия:** 1.13-improved  
**Контекст:** Разработано в рамках ВКР (Мосейчук М.Л., ЮФУ, 2026)  
**Назначение:** Реализация концепции «кибер-иммунной» защиты процесса сбора артефактов.

---

## 1. Назначение и цели

Монитор безопасности — это дополнительный слой защиты, который превращает UAC в более устойчивую к компрометации forensic-платформу.

### Основные цели:

- **Целостность политик и бинарников** — гарантировать, что профили сбора и исполняемые файлы UAC не были подменены.
- **Default Deny** — блокировать любые неизвестные операции по умолчанию.
- **Полный аудит** — фиксировать все критически важные действия во время сбора.
- **Непрерывный контроль** — проверять целостность не только при старте, но и во время работы.
- **Совместимость с расширенным сбором контейнеров** — монитор должен работать и при глубоком анализе docker/podman/nerdctl.

Монитор реализует принципы **Zero Trust** и **Cyber Immune** применительно к процессу цифровой криминалистики.

## 2. Архитектура

### 2.1 Основные компоненты

| Компонент | Файл / Функция | Назначение |
|-----------|----------------|----------|
| **Подпись белых списков** | `_sm_compute_whitelist_signature` / `_sm_verify_whitelist_file` | HMAC-подобная подпись (SHA-256 + секрет) для `allowed_profiles.txt` и `bin_whitelist.txt` |
| **Проверка профилей** | `_sm_check_profile_integrity` | Проверка хэша профиля + подписи whitelist |
| **Проверка бинарников** | `_sm_check_binary_integrity` | Проверка хэша исполняемых файлов из `bin/` |
| **Авторизация** | `_sm_authorize` | Центральная точка принятия решений (Default Deny) |
| **Аудит** | `_sm_log_event` | Запись всех событий в `uac_security_monitor_audit.log` |
| **Непрерывный контроль** | `_sm_continuous_integrity_check` | Перепроверка перед опасными операциями |
| **Инициализация** | `_sm_init` + авто-вызов | Самопроверка при старте UAC |

### 2.2 Модель угроз

Монитор защищает от следующих сценариев:

- Подмена `allowed_profiles.txt` злоумышленником
- Подмена бинарников UAC (например, `avml`, `statx` и др.)
- Выполнение несанкционированных команд через профиль
- Атака на сам монитор (tampering с whitelist'ами)

**Не защищает** (по дизайну):
- От атак на ядро ОС во время работы
- От физического доступа к машине с выключенным монитором
- От подмены самого `security_monitor.sh` (требует подписи всего пакета)

## 3. Белые списки и подписи

### 3.1 Структура файлов

**`security/policies/allowed_profiles.txt`**
```
full:sha256:<хэш>
ir_triage:sha256:<хэш>
...
___SM_WHITELIST_SIG___:sha256:<подпись>
```

**`security/policies/bin_whitelist.txt`**
```
./bin/linux/x86_64/statx:<sha256>
./bin/avml:<sha256>
...
___SM_WHITELIST_SIG___:sha256:<подпись>
```

### 3.2 Механизм подписи

Используется упрощённая HMAC-подобная конструкция:

```sh
signature = SHA256( content + secret )
```

Секрет захардкожен в `security_monitor.sh`:
```sh
__SM_WHITELIST_HMAC_SECRET="UAC-SM-2026-kiberimmune-v1.13"
```

**Важно:** Это не криптографически стойкий HSM. Цель — защита от случайной/быстрой подмены, а не от targeted attack с reverse-инжинирингом.

### 3.3 Генерация whitelist'ов

Скрипт `security/update_whitelists.sh` позволяет пересчитать подписи после обновления UAC.

Рекомендуется запускать после любых изменений в `bin/` или `profiles/`.

## 4. Интеграция с основным сбором

Монитор подключается в начале `uac`:

```sh
. "${__UAC_DIR}/security/security_monitor.sh"
_sm_init
```

Далее почти все критические операции проходят через `_sm_authorize`:

- Загрузка профиля
- Выполнение команд артефактов (`execute_artifact_command`)
- Запуск бинарников (`execute_binary`)
- Начало/завершение фаз сбора
- Финальная упаковка

При отказе авторизации сбор прерывается с фатальной ошибкой.

---

## 5. Интеграция со сбором контейнеров

Расширенный сборщик (`lib_collect_containers.sh`) тесно интегрирован с монитором:

- При `UAC_SECURITY_MONITOR=1` монитор инициализируется до вызова `_collect_containers`
- Все runtime-команды (`docker inspect`, `podman logs` и т.д.) в идеале должны проходить авторизацию (текущая реализация частично логирует через основной путь)
- Монитор проверяет целостность перед выполнением опасных операций внутри контейнеров (nsenter, export и т.д.)
- Аудит-лог фиксирует действия, связанные с контейнерами

Подробности — в [CONTAINER_COLLECTION.md](CONTAINER_COLLECTION.md).

## 6. Переменные окружения

| Переменная | Значение | Описание |
|------------|----------|---------|
| `UAC_SECURITY_MONITOR` | `1` / `0` | Включить/выключить монитор (по умолчанию 1) |
| `UAC_REGENERATE_WHITELIST` | `1` | Перегенерировать `bin_whitelist.txt` при старте |
| `__SM_POLICY_DIR` | путь | Переопределить расположение политик (для тестов) |

## 7. Журнал аудита

Файл: `uac_security_monitor_audit.log` (внутри выходного каталога и в temp).

Формат (pipe-separated):
```
timestamp|level|operation|details|decision|reason|user|hostname|pid|version
```

Ключевые события:
- `SM_INIT`
- `execute_artifact_command`
- `PROFILE_CHECK` / `BINARY_CHECK`
- `CONTINUOUS_CHECK`
- `BLOCK` (при отказе)

## 9. Ограничения и известные нюансы

- Контейнерный сборщик выполняет часть команд напрямую (не через `_sm_authorize`). Это отчасти компенсируется логированием на уровне `command_collector`.
- Подпись whitelist'ов использует захардкоженный секрет (достаточно для защиты от случайных изменений).
- Монитор не подписывает сам себя и скрипты `lib/`.
- При `UAC_SECURITY_MONITOR=0` вся защита отключается.

---

## 10. Рекомендации по использованию в продуктиве / для ВКР

1. Всегда оставляйте `UAC_SECURITY_MONITOR=1` (значение по умолчанию).
2. После обновления UAC пересобирайте whitelist'ы.
3. Регулярно проверяйте `uac_security_monitor_audit.log` на предмет подозрительных `BLOCK`.
4. Для демонстрации на защите ВКР используйте `./tests/run_vkr_tests.sh` — он даёт наглядные артефакты и аудит.
