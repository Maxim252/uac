## 2. Ключевые результаты

### 2.1. Функциональное покрытие

- **Подпись и проверка целостности белых списков** — полностью работоспособны. Подделка содержимого при сохранении старой подписи надёжно обнаруживается.
- **Default Deny** — неизвестные операции (`_sm_authorize`) корректно блокируются.
- **Непрерывный контроль** (`_sm_check_profile_integrity` / `_sm_check_binary_integrity`) — успешно проходит на реальных подписанных профилях и бинарниках проекта.
- **Аудит-журнал** — все важные события (`SM_INIT`, `execute_artifact_command`, проверки целостности) фиксируются.

### 2.2. Реальный сбор артефактов (самый важный раздел)

Выполнен полноценный запуск:

```bash
UAC_SECURITY_MONITOR=1 ./uac \
    -a "live_response/network/hostname.yaml,live_response/hardware/lscpu.yaml" \
    -f none \
    /tmp/uac-real-test-$$
```

**Результаты реального прогона:**
- Сбор завершился с кодом 0 без ошибок CLI.
- Создан выходной каталог с артефактами (`hostname.txt`, `lscpu.txt` и др.).
- В выходной каталог **скопирован** `uac_security_monitor_audit.log`.
- В журнале аудита:
  - Присутствует `SM_INIT`
  - Зафиксировано **1010** вызовов `execute_artifact_command` (реальный трафик команд во время сбора)
  - Нет ложных срабатываний «Profile not in whitelist»
- В `uac-*.log` зафиксировано успешное завершение сбора («Artifacts collection completed»).

**Вывод:** Монитор безопасности полностью интегрирован в процесс сбора и не нарушает его работоспособность.

### 2.3. Негативные сценарии

- Подделка белого списка (изменение данных при сохранении старой подписи) → **отклоняется**.
- Неверная подпись → **отклоняется**.
- Отсутствие подписи (legacy-файл) → разрешён с предупреждением (текущее проектное поведение).
- Неизвестная операция авторизации → **BLOCK + отказ** (Default Deny).

## 3. Выводы для ВКР

1. **Все ключевые функции Монитора безопасности** (`_sm_*`) протестированы как в изолированном режиме, так и в условиях реальной работы UAC.
2. **Механизм криптографической защиты** белых списков (HMAC-подобная подпись на базе SHA-256 + секрет) обеспечивает надёжное обнаружение tampering.
3. **Интеграция с основным сборщиком** — полная и корректная. Монитор не создаёт ложных блокировок при легитимном сборе и гарантирует ведение детального аудита всех выполняемых команд.
4. **Default Deny** + непрерывные проверки целостности работают в соответствии с концепцией «кибер-иммунной» защиты, заявленной в работе.
5. Тестовый сценарий может использоваться как регрессионный при дальнейшей доработке Монитора безопасности.

## 4. Тестирование сбора артефактов контейнеров совместно с Монитором безопасности

Отдельный комплексный тест был разработан специально для верификации взаимодействия расширенного сборщика контейнеров (`lib_collect_containers.sh`) и Монитора безопасности.

**Файл теста:** `tests/integration/test_containers_with_security_monitor.sh`

### 4.1 Объём тестирования

- Инициализация и само-проверки монитора перед запуском контейнерного сбора.
- Моковый (детерминированный) сбор через `docker`/`podman` моки с активным монитором.
- Проверка полной структуры артефактов:
  - Runtime-level: `info.txt`, `version.txt`, `system_df_v.txt`, journal logs.
  - Per-container: `inspect.json`, `logs.txt`, `suspicious_config.txt`, `config.json`, `hostconfig.json`, `securityopt.json`.
  - Filesystem export для stopped containers (`snapshot/filesystem.tar` + manifest).
- Авторизация контейнерных команд через `_sm_authorize "execute_artifact_command"`.
- Негативные сценарии:
  - Фиксация опасных контейнерных команд (`docker exec ... rm -rf`) в аудите.
  - Обнаружение подделки `allowed_profiles.txt` в контексте контейнерного сбора.
- Реальный сбор (когда docker/podman/nerdctl доступны и отвечают) с включённым монитором.
- Проверка отсутствия фатальных сбоев и корректности аудит-журнала.

### 4.2 Результаты (последний прогон)

- Все **13 проверок пройдены (100%)**.
- Монитор не нарушил ни одну фазу сбора контейнеров.
- Все ключевые forensic артефакты контейнеров (включая `suspicious_config.txt` и filesystem export stopped-контейнеров) создавались корректно.
- Механизм tamper detection работал даже при активном контейнере сборе.
- Реальный сбор на хосте с docker + podman + nerdctl успешно выполнился под контролем монитора.

### 4.3 Вывод для ВКР

Расширенный сбор артефактов из контейнеров (включая глубокий анализ конфигурации, capabilities, seccomp, filesystem export остановленных контейнеров и runtime forensics) полностью совместим с Монитором безопасности. Монитор не создаёт ложных блокировок и обеспечивает дополнительный слой аудита даже для команд контейнерных рантаймов.
